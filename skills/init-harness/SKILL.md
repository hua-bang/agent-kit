# Init Harness

为单个仓库建立最小可用的 Agent 工作入口。目标是让下一次修改能找到事实、遵守边界、执行检查并报告证据，不是生成一组看似完整的目录。

本技能首版尚未完成真实项目试用。不要把它当成已经验证的通用初始化器。

## 适用范围

- 新项目需要 Agent 开发入口。
- 已有项目需要整理分散的规则、知识和验证命令。
- 已有 harness 需要一次非破坏性的初始化补齐。

不负责批量改造多个仓库、重建业务架构、配置生产服务或迁移业务代码。跨仓库任务先确定一个目标仓库；父仓库只维护协调规则，子仓库保留自身权威规则。

## 工作模型

`Harness = AGENTS.md + Knowledge + Tool + Validate + Skills`

- **AGENTS.md**：简短入口、修改规则、安全边界、按需导航。
- **Knowledge**：当前实现事实、项目地图、环境和外部服务边界。
- **Tool**：确有重复需求时才提供的执行工具。
- **Validate**：原生检查入口、覆盖范围和本次执行证据。
- **Skills**：已经可复用的操作流程，不提前猜测未来需求。

Spec 可选：描述目标行为，不混入当前事实；历史决策与当前规范分开。

推荐入口与新增资产位置：

```text
AGENTS.md
harness/
├── knowledge/    # 按需
├── tools/        # 按需
├── validate/     # 按需
└── skills/       # 按需
```

这不是强制模板。现有文档、测试、CI、配置和脚本保留原位并链接复用；没有新增资产时不创建对应目录。即使没有工具或验证目录，也必须写清检查责任、缺口和报告要求。

## 1. 确认目标与安全边界

- 使用用户明确指定的仓库。目标不清晰时先询问，不自行改造当前目录或其他仓库。
- 查看 `git status --short --branch -uall`，记录基线分支与提交。有用户改动时不覆盖、移动、隐藏或清理；冲突时先询问。
- 本次授权只涵盖初始化；不默认包含提交、推送、部署、全局安装或外部服务访问。
- 明确禁区：生产数据库、真实身份认证、私有运维资料、密钥、破坏性迁移等。不要复述凭据。

## 2. 最小只读调查

先读取已有 Agent 入口（包括 `AGENTS.md`、`agents.md`、`CLAUDE.md` 等）、README、原生构建或依赖清单，再按需读取相关配置与少量实现。

只调查完成本轮所需内容；足够决策即停止，不为完整性遍历全仓库。

形成简短事实表：

| 项目 | 要记录的内容 |
| --- | --- |
| 项目地图 | 主要模块、入口与责任边界，并注明依据 |
| 工具链 | 运行时、包管理器、锁文件与版本约束 |
| 环境 | 最小配置、依赖服务、缺少环境时可做什么 |
| 检查 | 实际声明的命令、工作目录、覆盖范围与副作用 |
| 缺口 | 占位测试、未知 CI、未验证外部服务等 |

区分“代码已存在”“文档提出”“本次执行通过”。提交时间不能证明持续迭代，未发现测试文件不能直接推断完全无测试，CI 配置存在不能证明流水线通过。

## 3. 给出并确认本轮方案

列明复用什么、新增或修改哪些文件、首轮验证范围、执行风险和暂不处理项。

在已有规则上补齐，不另起一份重复事实源。大小写不同的入口文件也要先检查，避免在大小写不敏感文件系统中误覆盖。规则冲突时明确权威来源并统一引用，不同时保留互相矛盾的路径。

用户已明确授权对应方案时直接执行。范围不清、有冲突，或方案引入未经授权的副作用时先询问。

## 4. 建立最小入口

根级 `AGENTS.md` 至少说明：

1. 项目职责与最短地图入口。
2. 如何准备环境，以及不能访问的外部服务。
3. 任务开始前应读什么、修改归属与禁止操作。
4. 按改动类型选择的检查命令、工作目录与副作用。
5. 交付时如何报告证据、跳过原因与残余风险。

详细事实只维护一处，入口用相对链接导航。确有缺口时才添加 knowledge 文档、脱敏配置样例或检查工具。配置样例只能列出经实现确认的字段，使用占位值，不从真实环境文件复制秘密。

不要为了凑齐五个面创建空文件夹、空脚本、恒成功的测试或未经运行的“通过”报告。

## 5. 执行安全的验证闭环

- 优先使用仓库已有命令，不强制 pnpm、Node.js 或任何统一 runner。
- 执行前检查脚本链：自动修复 lint、代码生成、迁移、部署、安装钩子、网络请求和数据库写入均可能有副作用。
- 在已授权且风险可控时，选择一项小型、明确的改动演练“修改 → 检查 → 交付”；没有业务修改授权时，用本次 harness 文档改动演练，明确这不等于业务闭环通过。
- 本地无外部服务的检查优先，但静态检查与 mock 测试不能替代真实接口验收。
- 依赖或环境不满足时，不擅自安装、联网或访问生产。记录阻塞，给出最小下一步；可安全执行的文档或结构检查仍应完成。
- 每项证据记录命令、工作目录（使用仓库相对路径）、本次结果、检查范围及未覆盖内容。长日志和敏感输出不纳入版本控制。
- 命令成功退出不等于有效验证；识别占位命令。失败如实报告，不绕过检查来制造绿色结果。

## 6. 审阅与交付

检查最终 diff：没有无关改动、秘密、重复规则、断链或空模板。初始化应可重复执行；再次运行仅补实际缺口，已有完整入口无需改写。

最终报告：

- **新增与复用**：文件和权威来源。
- **实际检查**：执行命令、结果及覆盖范围。
- **未验证与阻塞**：环境、外部服务和测试缺口。
- **就绪状态**：仅文档入口就绪 / 本地检查可执行 / 小改动闭环已验证。
- **下一步**：一个最小、可执行的后续动作。

未得到提交或发布授权时保留本地改动，不自动创建提交或 PR。不要以“已生成目录”作为 harness 完成的依据。
